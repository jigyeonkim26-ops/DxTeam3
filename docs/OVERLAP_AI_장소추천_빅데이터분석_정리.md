# OVERLAP AI 장소 추천 기능 분석 정리

> 기준일: 2026-10-15
> 기준 코드: 로컬 `test/overlap-local-20261015` 작업 트리
> 문서 목적: 최종 산출물의 「빅데이터 분석 정의서」를 작성하기 위한 구현 근거 정리

## 근거 범위와 확인 상태

- 아래의 구현 설명은 현재 로컬 코드에서 확인한 내용이다. 핵심 파일은 `overlap/backend-fastapi/app/ai_recommendations.py`, `record_preference_analysis.py`, `recommendation_record_adapter.py`, `place_candidate_search_service.py`, `kakao.py`, `tavily_place_search_service.py`이다.
- 실제 테스트 계정의 최신 DB 자료와 추천 trace는 현재 작업 환경에서 확인할 수 없었다. 프로젝트 작업 디렉터리에 최신 JSONL/요청 로그가 없었고, 읽기 전용 DB 조회도 `OperationalError`로 실패했다. 따라서 기록 수, 실제 선호 분석값, 검색어, 추천 장소명·주소·점수는 임의로 채우지 않고 **확인 필요**로 표시한다.
- 백엔드 팀원이 최신 코드에서 A/B 두 테스트 계정 각각 앱 화면에 추천 카드 3개가 표시된 것을 확인했다고 전달했다. 이는 전달받은 화면 확인 결과이며, 이 문서 작성 환경에서 재실행하거나 trace로 독립 검증한 결과는 아니다. 세부 장소 정보와 HTTP 응답 상태는 확인되지 않았다.
- 로컬 Mock 회귀 테스트는 관련 11개 모듈에서 **181 passed, 0 failed, 2 warnings (9.17초)**였다. 실제 사용자 DB·Gemini·Kakao·Tavily를 대상으로 한 테스트 결과가 아니다.
- 코드에 `category-v6` 표기와 검색 진단의 `category-v5` 표기 및 세션 fingerprint의 `v5` 문자열이 함께 남아 있다. 배포된 서버 버전 및 실제 trace의 버전은 확인되지 않았으므로, 운영 로그의 파이프라인 버전은 배포 담당자가 별도 확인해야 한다.
- 실제 장소 기록의 원문, 계정 이메일, 사용자 ID, DB 접속정보와 API 비밀값은 본 문서에 넣지 않았다.

## 1. 기능 개요

| 항목 | 내용 |
|---|---|
| 기능명 | OVERLAP AI 개인화 장소 추천 |
| 기능 목적 | 로그인 사용자의 긍정적인 장소 기록에서 취향 근거를 구조화하고, 지역 내 실제 장소 후보를 찾아 근거와 적합도를 평가한 뒤 최대 3곳을 제시한다. |
| 사용자 입력 | 앱에 저장된 본인 장소 기록의 장소명·장소 연결 정보·감정·코멘트 등. 추천 요청에서 선택 지역을 전달할 수도 있다. |
| 사용자 결과 | 장소명, 주소, 위치, 개인화 키워드·추천 이유 등 추천 카드 데이터. 현재 코드상 첫 응답은 최대 3곳이다. |
| 전체 흐름 | 사용자 기록 조회 → 긍정 기록 선별 → 기록별 취향 분석 → 검색 의도/Query 구성 → Kakao 장소 후보 검색 → 지역·카테고리·방문 여부 검증 → 일부 후보 Tavily 근거 검증 → A/B 근거 및 개인화 적합도 평가 → 랭킹과 다양화 → 최대 3곳 응답 |

최초 추천과 다음 추천은 사용자별 세션을 사용한다. DB에서 필요한 기록 및 방문 장소 식별 정보를 DTO로 읽은 뒤 트랜잭션을 종료하고 외부 검색/LLM 작업을 수행하도록 구현되어 있다.

## 2. 데이터 준비

### 2.1 데이터 정의

| 데이터 항목 | 출처 | 의미 | AI 추천에서의 활용 |
|---|---|---|---|
| 사용자 ID | 인증 사용자 및 기록 DB | 기록 소유자 식별자 | 사용자별 기록·분석 캐시·추천 세션 분리. 모델 입력에는 전달하지 않음. |
| 기록 ID | 기록 DB | 기록 식별자 | 분석 응답을 원 기록에 연결하고 근거 검증에 사용 |
| 장소 ID / Kakao 장소 ID | 기록과 연결된 장소 DB | 방문 장소 및 외부 장소 식별자 | 장소 메타데이터 연결, 방문 장소 제외 |
| 장소명 | 장소 DB | 기록 대상 장소명 | LLM 입력의 장소명 및 취향 문맥. URL·이메일·전화번호 패턴을 정리하고 길이를 제한함. |
| 주소 | 장소 DB | 도로명 주소 우선, 없으면 저장 주소 | 선택 지역 추론 및 기록 문맥에 사용. LLM 요청 입력에는 포함하지 않음. |
| 위도·경도 | 장소 DB | 저장된 장소 좌표 | 추천 DTO에는 포함되지만 LLM 입력에는 포함하지 않음. |
| 코멘트(content) | 기록 DB | 사용자가 작성한 기록 본문 | LLM 입력의 주요 취향 근거. 민감 패턴을 정리하고 최대 500자 사용 |
| 감정값 | 기록 DB | 기록에 대한 사용자 감정 | `excellent`, `good`, `okay`만 긍정 취향 분석 입력으로 선별하고 각각 LOVE, LIKE, GOOD으로 매핑 |
| 작성 시각 | 기록 DB | 기록의 작성 시각 | 최신 기록 우선 정렬에 사용. 방문 날짜로 해석하지 않음 |
| Kakao 장소 카테고리·주소·좌표·장소 ID | Kakao Local 검색 결과 | 외부 실제 장소와 장소 유형 정보 | 장소 실재성, 지역, 중복, 카테고리 및 유형 검증 |
| 외부 근거 제목·본문·URL | Tavily 검색 결과 | 후보 장소의 공개 정보 | 장소 동일성과 구체 특징 근거를 확인할 때 제한적으로 사용 |

현재 추천 분석 입력에는 사용자 본인의 긍정 기록을 사용한다. 방문 여부 제외 정보는 감정과 무관하게 그 사용자의 전체 기록에서 장소 ID/이름만 별도 취합한다. 타 사용자 기록은 조회하지 않는다. 현재 레코드 스키마에는 방문 날짜가 없으므로 `visited_on`은 null이며 작성 시각으로 대체하지 않는다.

### 2.2 데이터 획득 방법

| 데이터/서비스 | 획득 방법 | 사용 목적 | 실제 사용 여부 |
|---|---|---|---|
| OVERLAP 사용자 기록 | FastAPI 인증 요청의 사용자 ID로 MySQL에서 본인 `Record`와 연결된 `Place` 조회 | 취향 입력과 방문 장소 제외 | 현재 코드에서 사용 |
| OpenRouter Chat Completions | 서버가 기록별 분석 입력을 JSON으로 보내고 JSON 객체 응답 수신 | 기록에 명시된 장소 유형, 취향 facet, 긍·부정 표현 구조화 | 현재 로컬 설정에서 사용하도록 구성. 실제 배포 호출 성공 여부는 최신 trace 확인 필요 |
| Kakao Local 키워드 장소 검색 | 서버가 지역·검색 의도로 키워드 검색 요청 | 실제 장소 후보·주소·좌표·카테고리 수집 | 코드에서 사용 |
| Tavily Search | 서버가 선별된 장소 후보에 대해 검색 요청 | 후보 장소와 외부 자료의 동일성 및 구체 특징 확인 | 코드에서 선택적으로 사용 |
| 추천 이미지 서비스 | 추천 응답의 이미지 보강 경로 | 카드 썸네일 제공 | 현재 코드에 연결됨. 추천 적합도 근거로 사용하지 않음 |

공식 참고 자료: [OpenRouter Chat Completions API](https://openrouter.ai/docs/api/api-reference/chat/create-a-chat-completion), [Kakao Local API 안내](https://developers.kakao.com/docs/en/local/dev-guide), [Tavily Search API](https://docs.tavily.com/documentation/api-reference/endpoint/search).

### 2.3 수집 데이터 예시

실제 A/B 계정의 원천 기록을 읽을 수 없어 실제 기록 예시 3~5건을 작성할 근거가 없다. 사용자 기록 원문을 임의로 만들거나 이전 버전의 테스트 예시를 실제 데이터처럼 넣지 않았다.

| 사용자 구분 | 장소 | 감정 | 코멘트 |
|---|---|---|---|
| A 테스트 사용자 | 확인 필요 | 확인 필요 | 실제 DB 기록 확인 필요 |
| A 테스트 사용자 | 확인 필요 | 확인 필요 | 실제 DB 기록 확인 필요 |
| B 테스트 사용자 | 확인 필요 | 확인 필요 | 실제 DB 기록 확인 필요 |

실제 기록 예시를 채우려면 개인정보를 제거한 최신 DB 조회 결과 또는 사용자가 승인한 비식별 샘플이 필요하다.

## 3. 전처리

### 3.1 전처리 과정

1. 인증된 사용자 ID로 본인 기록과 장소를 조회한다.
2. 추천 취향 분석에는 감정값 `excellent`, `good`, `okay`인 기록만 사용한다. 코드 매핑은 각각 LOVE, LIKE, GOOD이다. 다른 감정의 기록은 취향 분석 입력에서 제외된다.
3. 긍정 기록은 작성 시각과 기록 ID 내림차순으로 정렬한다. 선호 분석 서비스는 최대 30건을 선택한다.
4. 분석 DTO에는 기록 ID, 장소명, 기록 코멘트, 감정 코드, 장소 연결 정보 등을 구성한다. LLM에 보낼 때에는 `record_id`, 정리된 `place_name`, 코드의 기본 장소 유형 힌트, 사용 가능한 신뢰 카테고리, 감정 코드, 정리된 `content`로 축약한다. 사용자 ID·주소·좌표·작성 시각은 LLM payload에 넣지 않는다.
5. 장소명/코멘트의 URL·이메일·전화번호 패턴을 제거하고 공백을 정리한다. 장소명은 모델 입력에서 최대 120자, 코멘트는 최대 500자로 제한한다.
6. LLM 결과는 JSON 응답에서 추출하고 Pydantic 자료형 및 허용된 enum으로 검증한다. 응답의 evidence는 입력 장소명/코멘트 원문 구간과 대조하여 검증한다. 긍정 기록 안의 명시적 부정 표현은 별도 부정 facet으로 분리할 수 있다.
7. 사용자 전체 기록은 별도로 장소 ID/이름만 조회해 이전 방문 장소 제외에 사용한다. 취향 분석의 긍정 기록 집합과 방문 제외 집합은 목적이 다르다.
8. 도로명 주소 우선의 기존 장소 주소와 사용자가 명시한 지역 또는 자동 추론 지역을 검색에 전달한다. 자동 지역 확장 허용 여부는 사용자가 지역을 명시했는지에 따라 달라진다.
9. 외부 API 작업 전에 DB 읽기 트랜잭션을 rollback해 연결을 반환한다.

지역명 및 후보 카테고리의 정규화는 후보 검색/비교 단계에서 수행한다. DB에 저장된 장소 주소 원본을 수정하는 처리는 이 추천 파이프라인에서 확인되지 않았다.

### 3.2 전처리 데이터 예시

아래는 데이터 모양만 설명하는 **비실사용자 예시**이며, 실제 A/B 기록이 아니다.

**원본 기록 형태(예시)**

- 장소: `[장소명]`
- 감정: `good`
- 코멘트: `[사용자가 작성한 문장]`
- 저장 장소 정보: 장소 ID, 주소, 좌표

**전처리 후 LLM 입력 형태(필드 예시)**

```json
{
  "record_id": "실제 정수 ID",
  "place_name": "정리 및 길이 제한된 장소명",
  "place_type_hint": "코드의 기본 분석 결과 또는 unknown",
  "trusted_category": "신뢰 메타데이터가 있을 때만 값, 그 외 빈 문자열",
  "emotion": "LIKE",
  "content": "개인정보 패턴 정리 및 500자 이내 코멘트"
}
```

실제 A/B 사용자의 분석 입력 및 반환 facet은 최신 trace가 없어 확인할 수 없다.

## 4. 데이터 분석

### 4.1 데이터 분석 목표

긍정적인 장소 기록에서 사용자가 실제로 표현한 선호 대상·특징과 장소 분야를 구조화해, 기록의 근거를 벗어나지 않는 개인화 검색과 추천에 활용한다. 명시적 부정 취향도 구분해 직접 충돌하는 후보를 제한한다. 모델 자체가 장소를 만들어내는 것이 아니라 실제 장소 후보는 별도 장소 검색에서 확보한다.

### 4.2 데이터 분석 시나리오

| 단계 | 입력 | 처리 | 출력 |
|---|---|---|---|
| 1. 기록 조회 | 인증된 사용자 ID | 본인 긍정 기록과 전체 방문 장소 ID/이름을 각각 조회 | 사용자별 기록 DTO와 방문 제외 식별 정보 |
| 2. 기록 선별·정리 | 긍정 기록 DTO | 최신순 정렬, 최대 30건, 텍스트 개인정보 패턴 정리 및 길이 제한 | 제한된 분석 입력 |
| 3. 기록 취향 분석 | 기록 ID·장소명·감정·코멘트 | OpenRouter Chat Completions JSON Mode로 기록별 분석; 응답 스키마·근거 검증 | 기록별 place type, category, facet, polarity, evidence, confidence 등 |
| 4. 선호 프로파일 | 검증된 기록 분석 | 분석 가능 category/facet를 취향 근거로 집계하고 카테고리 간 검색 의도를 준비 | 사용자별 검색용 선호 분석 |
| 5. 검색 Query 생성 | 지역, 선호 facet/category/type | 구체 의도와 넓은 장소 유형 검색어를 생성하고 여러 의도를 분산·중복 억제 | Kakao 키워드 Query 목록 |
| 6. Kakao 후보 검색 | Query와 지역 | Kakao Local 키워드 검색, ID 기준 중복 제거 및 후보 수집 | 실제 장소 ID·이름·주소·좌표·카테고리 후보 |
| 7. 후보 필터 | 후보와 요청 지역·방문 목록·카테고리 | 지역, 카테고리/유형, 중복, 방문 여부 확인 | 필터 통과 후보 및 진단 탈락 사유 |
| 8. 외부 근거 확인 | 일부 우선 후보 및 선호 facet | Tavily 결과의 URL, 장소 동일성, 명시적 특징 근거 평가 | 확인된 특징 evidence 또는 미확인/실패 상태 |
| 9. 개인화 평가 | 후보 유형, 검증 특징, 선호 분석, 부정 facet | 구체 특징 연결과 반복 분야 선호를 등급 및 적합도에 반영 | A/B 적격 추천 후보 |
| 10. 랭킹·세션 | 적격 후보 | 적합도 중심 정렬, 근접 후보 사이 취향 다양성 고려, 방문/기노출 장소 배제 | 사용자별 최대 3곳과 다음 추천 세션 |
| 11. 설명·응답 | 최종 장소 및 근거 | 확인된 취향 키워드와 근거 수준에 맞춘 이유/태그 구성; 이미지 보강 가능 | 추천 카드 응답 |

현재 route는 요청의 `category` 파라미터를 호환을 위해 받지만 결과는 전체 취향 기반으로 처리한다. 지역 자동 확장은 사용자가 명시적으로 지역을 선택하지 않은 경우에만 허용한다.

### 4.3 선호 분석 항목

현재 프롬프트/모델 구조에 정의된 분석 항목은 다음과 같다.

| 분석 항목 | 의미 | 추천에서의 활용 |
|---|---|---|
| `record_id` | 분석 결과의 원 기록 연결 키 | 기록 근거 추적 |
| `place_type` | food, bar, cafe, nature, activity, unknown 중 장소 유형 | 기본 유형 추론 및 검색/유형 비교 |
| `place_type_label` | 근거가 있는 장소 유형의 설명 라벨 | 내부 장소 유형 근거 |
| `place_type_evidence` | 장소 유형 판단의 기록상 근거 | 유형 신뢰도 검증 |
| `categories` | all, food, bar, cafe, nature, activity 분야 배열 | 사용자 선호 분야 집계 및 검색 분산 |
| `facets[].target_kind` | menu, drink, food, ambience, space, activity, scenery, service, facility, other | 선호가 가리키는 대상 종류 |
| `facets[].target_text` | 장소명 또는 코멘트에 실제 나타난 짧은 대상 구절 | 구체 선호 검색·매칭 |
| `facets[].features` | 기록에서 명시된 특징 문구 배열 | 장소 근거와 비교할 구체 취향 |
| `facets[].polarity` | liked, disliked, neutral | 긍정/부정/중립 근거 분리 |
| `facets[].evidence` | 원문에 실제 존재하는 짧은 근거 문구 | 기록 원문 근거 검증 |
| `facets[].confidence` | 모델이 제시한 분석 신뢰값 | 유효성 점검 및 추천 분석 입력 |
| `evidence_status` | provider 성공, fallback/사용불가 등 코드 상태 | 분석 신뢰와 fallback 구분 |

개별 취향 단어 목록을 완성형 사전으로 한정하는 설계가 아니라, 기록 문맥에서 나온 동적 facet을 검증하는 구조다. 일부 보수적인 로컬 fallback 용어 처리는 코드에 존재한다. 그 용어 목록 자체를 일반 사용자 취향의 전체 목록으로 해석해서는 안 된다.

### 4.4 검색 Query 생성

Query는 지역 검색 문자열과 분석된 선호 facet 또는 장소 분야/유형의 검색 의도를 조합한다. 후보 검색 서비스는 구체 취향을 우선 사용하면서, 검색 결과가 부족한 경우 해당 취향의 보다 일반적인 장소 유형 의도를 사용하고, 카테고리/의도를 교차 배치해 한 분야가 제한된 검색 예산을 독점하지 않도록 구성한다. Kakao 호출 상한은 12회다. 이 값은 상한이며 매번 12회 모두 호출한다는 의미가 아니다.

최신 A/B trace 및 생성 Query 목록이 없어 실제 테스트에서 사용된 Query 예시 3~5개를 확인할 수 없다. 다음은 **실제 실행 Query가 아닌 형식 설명**이다.

```text
{정규화한 지역} + {기록에서 검증된 구체 facet}
{정규화한 지역} + {선호 분야와 연결 가능한 일반 장소 유형}
```

최종 산출물에 실제 Query 사례를 기재하려면 최신 요청의 `generated_queries`/검색 Query 이벤트를 개인정보 제거 후 확보해야 한다. 과거 로그의 Query를 최신 실행 예시로 대체하지 않았다.

### 4.5 후보 장소 검색 및 검증

1. Kakao Local 키워드 검색 결과로 실제 외부 장소 ID, 이름, 주소, 좌표, 카테고리/장소 URL을 확보한다.
2. Kakao 장소 ID로 중복을 제거한다. 실제 지점이 다른 경우 별도 장소 ID와 위치를 확인한다.
3. 지역 비교 및 자동 지역 확장 정책을 적용한다. 명시 지역을 임의로 넓히지 않으며 자동 추론 지역에서만 조건부 확장한다.
4. 후보의 Kakao 카테고리 그룹 코드/카테고리명을 내부 분류로 연결한다. 유형이 확인되지 않은 후보를 단지 검색됐다는 이유로 자동 허용하지 않는다.
5. 사용자의 전체 기록에서 수집한 방문 장소 ID/이름과 비교해 이미 방문한 장소를 제외한다.
6. 후보 중 제한된 수를 Tavily로 검증한다. URL 유효성, 결과가 실제 해당 후보를 설명하는지, 이름/지역 동일성, 사용자 취향 특징의 직접 근거를 각각 살핀다. 검색 결과에 키워드만 언급된 경우와 해당 장소 특징이 확인된 경우는 구분한다.
7. A/B 개인화 근거를 계산한다. A는 검증된 장소 특징과 긍정 facet의 구체 연결을 요구한다. B는 Kakao에서 확인되는 적절한 세부 유형과 사용자 기록의 긍정 분야/취향 연결을 인정할 수 있지만, 확인되지 않은 메뉴·시설·분위기를 설명에 넣지 않는다. 단순히 검색 결과가 있다는 것만으로 통과하지 않는다.
8. 최종 적격 후보가 부족해도 무관한 장소로 채우지 않는다. 후보 부족/검색 실패/세션 소진은 서로 다른 응답·진단 상태로 다룬다.

현재 코드 상한: Kakao 최대 12회, Tavily 최대 6회, Kakao 고유 후보 최대 50개, Tavily 검증 대상 최대 6개. 상한과 실제 사용량은 다를 수 있다. Tavily는 모든 추천의 필수 관문이 아니며, 확인된 Kakao 유형과 사용자 기록만으로 B 근거가 충분한 후보는 그 근거 범위 내에서 평가될 수 있다.

### 4.6 Ranking 방식

| Ranking 요소 | 의미 | 추천 순위에 미치는 영향 |
|---|---|---|
| 검증된 구체 특징 일치 | 장소의 근거 자료와 사용자의 긍정 facet 연결 | A급 근거 및 높은 개인화 우선순위 |
| Kakao 확인 장소 유형 | 검색 결과의 확인된 분류/세부 유형과 긍정 취향 분야의 연결 | 일정 기준을 만족하면 구체 특징 외 B급 근거가 될 수 있음 |
| 반복적인 분야 선호 | 서로 다른 긍정 기록에서 확인된 반복 분야/대상 | 단일 우연 기록보다 분야 선호 근거를 강화; 최소 기록/대상 조건이 코드에 있음 |
| 감정 및 기록 근거 상태 | 긍정 감정 강도와 분석 evidence 상태 | 근거의 신뢰도·가중치에 반영 |
| 부정 취향 충돌 | 명시적으로 싫다고 한 특징과 후보의 직접 충돌 | 직접 충돌하면 hard exclusion 가능 |
| 지역 및 장소 실재성 | 실제 후보 ID/주소 및 지역 적합성 | 안전상 hard filter |
| 방문 중복 | 사용자 전체 기록의 기존 방문 장소와 동일성 | 기존 제외 정책에 따라 제외 |
| 후보 간 취향 다양성 | 적격 장소들이 반영하는 서로 다른 확인 취향 | 점수가 비슷한 후보 간 보조 고려. 적합성이 크게 낮은 장소를 강제 삽입하지 않음 |
| 검색 순서 | 탐색 우선순위 | 랭킹의 주 근거가 아니라 동점 보조 정보 |

코드에는 A/B 후보 점수 및 반복 분야 선호 임계값이 있으나, 이 문서에서는 코드에서 확인한 정책을 말로 설명하고 임의의 산식/가중치를 추가하지 않았다. 최종 반환은 최대 3곳이며 3곳을 채우기 위한 하한 보장은 없다.

| 항목 | 확인 결과 |
|---|---|
| 전체 기록 수 | 확인 필요: DB 읽기 실패 |

| 주요 category / facet / place type | 확인 필요: 실제 최신 분석 응답 없음 |
| 실제 생성 검색 Query | 확인 필요: 최신 Query 로그 없음 |
| 최신 최종 화면 카드 수 | 3개 표시를 백엔드 팀원이 확인했다고 전달받음. 이 문서에서 독립 검증하지 않음 |

| HTTP 상태 및 처리 시간 | 확인 필요 |

### 5.3 A/B 비교

| 구분 | A 사용자 (usera 테스트 계정) | B 사용자 (userb 테스트 계정) |
|---|---|---|
| 전체 기록 수 | 확인 필요 | 확인 필요 |
| 긍정 기록 수 | 확인 필요 | 확인 필요 |
| 주요 취향 | 자연·산책 성향 계정으로 지정됨. 실제 최신 분석값 확인 필요 | 미술관·카페 성향 계정으로 지정됨. 실제 최신 분석값 확인 필요 |

카드 수만으로 A/B 개인화가 서로 다른 취향을 반영했는지 판단할 수 없다. 결과 비교를 완성하려면 동일 최신 배포 코드 버전의 trace_id, 비식별 category/facet 집계, 실제 응답의 장소 ID·주소·등급·근거 및 점수가 필요하다.

## 6. 모델 생성 및 학습

### 6.1 모델링 목표

사용자 기록을 사전학습 LLM API로 분석해 추천에 사용할 기록 기반 선호 정보를 구조화한다. 모델 응답은 기록 원문 근거 및 자료형 검증을 거쳐 장소 검색·개인화 로직에 입력된다.

### 6.2 사용 모델

| 설정 | 현재 확인 내용 |
|---|---|
| Provider | 로컬 프로젝트에서 로드된 `LLM_PROVIDER=openrouter` |
| Model | 로컬 프로젝트에서 로드된 `google/gemini-3.1-flash-lite` |
| API 방식 | OpenRouter Chat Completions HTTP API, JSON object response mode |
| Endpoint | `https://openrouter.ai/api/v1/chat/completions` |
| 배포 서버의 실제 설정 | 확인 필요. 로컬 환경 설정이 배포 환경과 같다고 단정할 수 없음 |

API 키 값은 문서에 포함하지 않았다. 위 모델명은 현재 로컬 실행환경의 설정값 확인이며, 최신 운영 trace에서 사용된 모델이라는 뜻은 아니다.

### 6.3 학습 방법

- 자체 AI 모델 생성 없음
- 자체 모델 학습 없음
- Fine-tuning 없음
- 학습 데이터셋 구축 없음
- 사전학습 LLM을 API로 활용
- 실제 사용자 기록을 제한·정리해 inference 입력으로 사용
- 프롬프트 기반 JSON 분석 결과를 장소 추천 로직에 활용
- epoch, loss, optimizer, train/validation split 등 자체 학습 지표 없음

### 6.4 모델 출력 결과

실제 A/B 분석 응답을 확인할 수 없으므로 아래는 **응답 필드 구조의 비실데이터 예시**다. 실제 사용자 선호나 기록 내용으로 오해되지 않도록 값은 자리표시자로 표시했다.

```json
{
  "record_id": "실제 정수 ID",
  "place_type": "food | bar | cafe | nature | activity | unknown 중 하나",
  "place_type_label": "근거가 있는 경우의 유형 라벨",
  "place_type_evidence": "입력 원문 근거 또는 null",
  "categories": ["분류 enum 값"],
  "facets": [
    {
      "target_kind": "menu | drink | food | ambience | space | activity | scenery | service | facility | other 중 하나",
```

| 응답시간·HTTP 상태 | 최신 서버 요청 trace/접속 로그 | 확인 필요 |

| 이미지 보강 | 현재 코드의 추천 이미지 서비스 | 추천 응답 썸네일 보강; 개인화 근거로 간주하지 않음 |

## 9. 예외 및 Fallback 처리

| 상황 | 현재 코드에서 확인한 처리 |
|---|---|
| 긍정 분석 기록 없음 | 빈 추천 응답과 empty 상태를 반환 |
| 기록이 있으나 선택 지역 추론 불가 | 현재 category 경로는 지역 입력 오류 응답으로 처리할 수 있음 |
| OpenRouter 설정 누락 | 기록 기반의 제한적인 local fallback 분석 경로 사용 |
| LLM HTTP/응답/파싱/검증 실패 | 오류/사용불가 상태를 구분하며 안전한 fallback 처리. 모델 실패를 provider 성공으로 취급하지 않음 |
| fallback으로 안전한 검색 입력을 만들 수 없음 | 검색 불가로 처리하고 서비스 오류 응답을 반환할 수 있음 |
| Kakao 정상 빈 검색 결과 | 검색 결과 없음으로 구분; 다른 Query/후속 탐색은 잔여 예산과 파이프라인 조건에 따름 |
| Kakao 서비스 사용 불가 | 후보 없음과 별개로 서비스 오류 처리 |
| 지역·방문·카테고리 부적합 | 해당 후보 제외 및 진단 이유 기록 |
| Tavily 무응답/검색 실패/동일성 불충분 | 구체 특징 근거 없음으로 처리. 확인되지 않은 특징을 만들어내지 않음. 다른 Kakao 유형 근거가 충분한 후보의 B 자격은 별도 평가 |
| 적격 후보 부족 | 가능한 적격 수만 반환; 무관한 후보로 최대 3곳을 채우지 않음 |
| 후보 모두 소진 | 사용자별 추천 세션에 따라 다음 후보 또는 소진 상태 반환; 실제 최신 A/B 세션 trace는 확인 필요 |
| 캐시 적중 | 사용자 및 기록 fingerprint를 기준으로 분석/세션 캐시를 재사용하는 경로가 있음. TTL은 코드에서 관리 |
| API 키/비밀 설정 | 키 값은 문서나 일반 진단에 기록하지 않음 |

정확한 최신 배포 동작과 cache invalidation 확인을 위해 `OVERLAP_CODE_VERSION` 또는 `GIT_COMMIT` 값이 포함된 최근 trace를 추가 확보해야 한다. 현재 로컬 코드의 category pipeline 태그와 세션 버전 문자열이 일치하지 않는 부분이 있어, 최종 산출문서의 운영 버전 표기는 배포 코드 확인 후 확정하는 편이 안전하다.

| 데이터 분석 목표 | 실제 긍정 기록에서 선호 분야, 장소 유형, 구체 취향 및 부정 특징을 근거와 함께 구조화해 개인화 장소 검색·추천에 사용 |

| 학습 방법 | 자체 학습·Fine-tuning·학습 데이터셋 없음. 기록을 프롬프트 입력으로 보내 API inference 수행. epoch/loss/split 없음 |
