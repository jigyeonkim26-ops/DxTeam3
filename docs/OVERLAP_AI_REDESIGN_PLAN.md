# OVERLAP AI 추천 알고리즘 개선 설계안

> 작성 기준: 사용자가 제공한 `AI_RECOMMENDATION_LOGIC_ANALYSIS.md`의 **미커밋 변경을 포함한 로컬 코드 분석 보고서**와 두 테스트 계정의 실제 피드백. 본 문서는 제안 설계서이며, 현재 로컬 코드 수정·실행·실제 외부 API 검증을 완료했다는 뜻이 아니다.

## 1. 목표와 성공 기준

**목표**: 분야가 섞인 긍정 기록에서도 `장소 유형 → 좋아한 대상 → 구체적 이유`를 잃지 않고, 선택한 분야 안에서 실제 Kakao 장소를 최대 3곳 추천한다. 3곳을 억지로 채우거나 메뉴·분위기를 지어내지 않는다.

- 사용자 선택 분야: `all`, `food`, `bar`, `cafe`, `nature`, `activity` (기본 `all`).
- 선택 분야와 무관한 추천은 배제. 분야가 모호하면 근거를 확인한 뒤 채택하며, 근거가 부족하면 제외.
- 구체적인 메뉴·분위기는 검증 가능한 검색 근거가 있을 때만 추천 이유에 단정적으로 사용.
- Kakao Place ID, 명칭, 주소, 좌표는 카카오 검증 결과를 그대로 사용.
- 후보가 충분하면 **최대 3곳**. 0·1·2곳도 허용하며 품질 유지.
- 실제 계정의 추천 개수·관련성과 테스트 목(mock) 결과를 구분해 보고.

## 2. 현재 코드에서 확인된 제약

1. 긍정 기록 `excellent/good/okay`만 조회. 추천 DTO에는 본문/장소명/주소/좌표/감정/Kakao ID가 있지만 **장소의 표준 분류·구체적인 긍정 측면은 별도 구조로 보존하지 않음**.
2. OpenRouter가 사용자 전체 기록을 선호 키워드 최대 5개로 요약하며, 기록별 `장소 유형 + 특징` 연결을 잃기 쉬움.
3. Tavily가 웹 제목을 장소명으로 정리해 10곳 내 후보를 생성, Kakao가 그 명칭을 다시 검증. 웹 제목과 실제 상호가 다른 경우 후보를 놓치기 쉬움.
4. Tavily는 첫 기록 주소 토큰을 검색 지역으로 사용. 광주/대구 혼합 기록에 취약.
5. 제한된 동의어 사전과 고정 기준 0.18의 근거 적합성 필터가 다양한 한국어 메뉴/분위기 표현을 충분히 다루기 어려움.
6. `refresh=true`는 새로운 외부 검색이 아니라 캐시된 후보 풀의 다음 부분을 반환. `exclude_place_ids`, `previous_place_ids`는 문서 시점에 읽지 않음.
7. 결과 풀은 프로세스 내부 20분 캐시. 다중 서버 인스턴스에선 갱신 상태가 달라질 수 있음.
8. Flutter timeout은 180초. 반복적인 외부 호출은 사용성·비용에 부담.

## 3. 목표 추천 흐름

```
(1) 선택 분야(category) + 추천 지역(region) 결정
 ↓
(2) 사용자 긍정 기록 → 기록별 취향 맥락(facets) 구조화
 ↓
(3) 선택 분야에 관련된 선호 묶음 생성; 분야 밖 정보는 제한적인 보조 근거로 활용
 ↓
(4) 분야 + 구체적인 선호 + 지역 기반 Kakao 후보 발굴
 ↓
(5) Kakao 장소 유형·ID·좌표 확인, 방문 장소·중복 제외
 ↓
(6) Tavily/신뢰 가능한 근거로 해당 *정확한 장소*의 메뉴·분위기·특징 보강
 ↓
(7) 필수 유형 조건과 근거 수준 확인 → 소프트 선호 적합도 순위
 ↓
(8) OpenRouter는 검증된 후보 안에서 순위와 근거 있는 한국어 설명 정리
 ↓
(9) 검증된 상위 최대 3곳 반환 + 이미지 보강 + 분야별 결과 캐시
```

**중요**: Kakao 우선 탐색만으로 모든 장소가 검색된다고 가정하지 않는다. 보완 탐색에는 Tavily의 후보를 이용하되, 최종 선택은 반드시 동일한 Kakao 장소로 연결한다. 웹 문서의 특정 메뉴 언급은 장소 동일성·지역·시점·문맥이 확인됐을 때만 활용한다.

## 4. 기록별 취향(facet) 데이터 예시

기존 DB 변경 없이 DTO/임시 내부 모델부터 도입한다. 실제 Record/Place 모델의 기존 필드를 먼저 확인한다.

```json
{
  "record_id": 123,
  "place_type": "bar",
  "place_type_evidence": "Kakao category or reliable existing place metadata",
  "emotion": "excellent",
  "positive_aspects": [
    {"kind": "menu", "value": "유자하이볼", "evidence": "기록에 해당 메뉴를 좋게 평가함"},
    {"kind": "menu", "value": "꼬치", "evidence": "기록에 해당 메뉴를 좋게 평가함"}
  ],
  "region": "광주광역시"
}
```

`place_type`을 알 수 없으면 `unknown`으로 두고, 필요시 Kakao의 실제 장소 분류 또는 기존 기록 메타데이터로 보완한다. 모델이 한 번 본 텍스트만으로 특정 상호의 업종을 확정했다고 기록하지 않는다. `bar`와 `food`처럼 겹치는 분류는 보조 태그를 허용한다.

추출 예시:

| 기록 문장 | 분야/대상 | 선호 맥락 | 잘못된 검색 |
|---|---|---|---|
| 유자하이볼·꼬치 맛있다 | 술집 / 음료·안주 | 해당 메뉴가 있는 다른 술집 | 맛있는 아무 장소 |
| 카페가 조용하고 넓다 | 카페 / 분위기·공간 | 조용하고 넓은 다른 카페 | 조용한 농장·넓은 주차장 |
| 야구 응원 분위기가 좋다 | 스포츠 / 관람 활동 | 경기 관람·응원 관련 장소 | 분위기 좋은 카페 |
| 무등산의 경치가 좋다 | 자연 / 조망 | 경관 근거가 있는 전망·공원 | 무관한 상업시설 |

## 5. 카테고리별 정책

- `all`: 검증된 주요 선호를 종합. 의도적으로 모든 분야를 1곳씩 채우지 않음.
- `food`: 음식점. 메뉴·음식 종류 중심. `bar`와 겹칠 수 있으나 사용자가 맛집을 선택했으면 식사 맥락 우선.
- `bar`: 술집·이자카야·펍. Kakao의 일반 음식점 코드만으로는 부족할 수 있으니 **세부 업종 + 검색 근거** 함께 사용.
- `cafe`: 실제 카페만. 장소명에 `조용함`이 없어도 출처에서 분위기가 확인되면 선호로 인정.
- `nature`: 공원·산책로·전망대 등 비상업적 장소 포함. Kakao 단일 분류 코드에만 의존하지 않음.
- `activity`: 스포츠 관람·공연·전시 등 활동 기반. 적절한 하위 유형과 방문 의도가 있어야 함.

**가장 중요한 정책**: 선택 분야와 실제 장소 유형의 일치는 필수 조건(hard gate). `조용함`, `넓음`, `유자하이볼` 등의 세부 취향은 가중치 있는 순위 신호(soft relevance)다. `유자하이볼`을 판매한다는 검증된 증거가 없으면 이유에 판매 사실을 쓰지 않는다.

## 6. 후보 검색·증거 연결

### 현재 대비 개선

- `Tavily 웹 제목 → Kakao 상호명 완전 매칭` 일변도에서 탈피.
- 먼저 Kakao에 `지역 + 업종 + 구체적인 특징/메뉴` 등 2~3가지 상보적인 질의를 사용해 **실제 장소 ID를 확보**.
- 카카오에서 확인된 상호명/지역 조합으로 Tavily를 조회해 정확한 **동일 장소**에 대한 메뉴·분위기 등의 근거를 결합.
- 후보가 충분하지 않으면 Tavily에서 발견한 상호를 Kakao로 역검증하는 보조 경로 이용.
- URL·검색 스니펫은 출처 증거로 관리. 검색 결과 제목만으로 메뉴 판매·공간 특징을 사실로 단정하지 않음.
- 중복 제거는 Kakao Place ID 기준, 사용자의 기존 방문 장소도 같은 기준 우선.
- 외부 호출 수는 기존 예산(예: Kakao 최대 6회)을 우선 보존하고 **실제 결과 수와 비용 측정 후** 조정.

### 검색 예시

- `bar` + `광주`: `광주 유자하이볼 이자카야`, `광주 꼬치 술집`
- `cafe` + `광주`: `광주 조용한 카페`, `광주 넓은 좌석 카페`
- `nature` + `광주`: `광주 전망 공원`, `광주 산책로`

검색어는 **실제 선택 분야와 기록에서 나온 선호**로 생성하고 근거 없는 취향을 확장하지 않는다.

## 7. 지역 정책

사용자 기록이 광주와 대구에 섞여 있다면 첫 기록의 주소만 사용하는 것은 부정확하다.

- MVP: 사용자가 추천 지역을 명시적으로 선택하도록 작은 컨트롤 제공. UI 추가가 어렵다면 현재 지도 중심/현재 위치를 기본값으로 사용하되, 적용 지역을 화면에 명시하고 변경 가능하게 설계.
- `region`이 명시되면 해당 지역을 API 전체 경로에서 일관되게 사용.
- 주소 표기는 행정구역 별칭 정규화. 기준 지역이 불명확하면 명시적으로 안내하고 임의 단일 지역으로 확정하지 않음.
- 예시 API: `GET /ai/recommendations?category=bar&region=광주광역시`; 실제 API 형식은 기존 코드와 호환성을 조사한 뒤 결정.

## 8. 관련성 평가와 추천 이유

- 1차 **자격 판단**: 실제 Kakao POI, 필드 완전성, 선택 분야 적합, 방문 장소 아님, 명백히 잘못된 외부 근거 아님.
- 2차 **연관성 순위**: 구체적 메뉴/활동의 근거, 분위기/장소 특성 근거, 긍정 기록에서 반복된 취향, 추천의 새로움 및 후보 간 중복.
- 점수는 내부 정렬 신호로 사용하며, LLM에서 받은 0~1 수치를 사용자 선호의 확률로 해석하지 않음. 가중치/임계값은 회귀 사례를 수집해 조정.
- LLM은 후보 ID만 선택하고 설명을 정리. 존재하지 않는 장소를 제안하거나 증거 없는 메뉴를 주장할 권한은 없음.
- LLM이 빈 배열/오류를 내면 **적합성 검증된 풀**을 근거와 함께 안전하게 반환하되, 추천 이유를 새로 지어내지 않음.
- 분야 기록이 거의 없으면 `해당 분야 기록이 많지 않아 일반적인 선호를 참고했어요` 등의 명확한 안내를 검토. 미확인 메뉴를 개인화 근거로 사용하지 않음.

## 9. 캐시/새로고침/성능

- 캐시 키: `user_id + category + region + positive_records_fingerprint + recommendation_logic_version`.
- 첫 페이지 상위 최대 3곳, 다음 페이지는 같은 분야·지역의 검증 후보 풀에서 제공. 모두 소진 시 처음 페이지로 복귀.
- `refresh=true`가 현재 캐시 페이지 이동이라는 의미라면 화면 문구는 `다른 장소 보기`처럼 동작에 맞게 조정. 새 외부 검색은 별도 action/rate limit 설계.
- 프로세스 메모리 캐시는 단일 서버 시연의 임시안. 다중 worker 배포 시 DB/Redis 혹은 서버 독립 cursor 설계가 필요.
- 외부 호출 중 DB 트랜잭션/커넥션을 점유하지 않게 유지. 추천 단계별 소요시간, 요청 당 유료 호출 수, 비용 지표 추가.
- 추천 기록 입력에는 길이·건수 상한 및 민감정보 제거/요약을 적용하고, 외부 LLM에 사용자 기록 전문을 과다 전송하지 않도록 개선.

## 10. 구현 단계: 한 번에 전면 수정하지 말 것

### 0단계. 기준선 확보 (코드 변경 최소)
- Git 미커밋 상태 보존, 이전 작업 재설정 금지.
- 두 실제 테스트 계정에서 현재 추천의 분야 적합도·근거·후보 수·지연시간 기록.
- 주요 로그: 기록 수 → 추출 맥락 수 → 카테고리 일치 후보 수 → Kakao 검증 수 → 근거 확보 수 → 최종 0~3개.

### 1단계. 백엔드 입력/프로필 구조
- `category` 파라미터(기본 `all`) 및 검증 추가, 선택 지역은 옵션으로 별도.
- Record adapter 확장 또는 새 service에서 기록별 place_type / preferred_aspects 구조화.
- `all`, `bar`, `cafe`, `nature` 등 분야별 선호 추출 테스트. 이 단계에서 Flutter 전체 UI 변경 금지.

### 2단계. 후보 검색과 검증
- Kakao 실장소 우선 탐색 + Tavily 해당 장소 근거 조회. 부족할 때 Tavily 후보 → Kakao 검증 보조.
- 선택 분야와 실제 Kakao POI 유형 일치 테스트. 혼합 도시 및 특수 장소 분류 테스트.
- 추출 근거가 부족해도 검색 후보를 무조건 부풀리지 않음.

### 3단계. 순위·응답·캐시
- hard category gate + soft evidence ranking, 안전한 fallback.
- 캐시 키에 category/region/기록 지문 포함. 새로고침 소진 후 최초 추천 복귀.
- 인증 사용자별 격리, 잘못된 장소 ID·빈 LLM 응답 테스트.

### 4단계. Flutter 연결 및 E2E
- 칩 6개, 로딩/빈 결과 처리, 빠른 탭으로 발생하는 응답 역전 방지.
- 기존 카드·이미지·지도 핀·상세·즐겨찾기 보존.
- 실제 혼합 기록 계정과 자연 계정에서 각각 검증.

## 11. 회귀 평가 시나리오

| 테스트 | 입력 조건 | 통과 조건 |
|---|---|---|
| 혼합 기록-술집 | 꼬치·유자하이볼 술집 + 카페 + 스포츠 | `bar` 선택 시 실제 술집만, 메뉴 언급은 근거 있을 때만 |
| 혼합 기록-카페 | 조용하고 넓은 카페 기록 | `cafe` 선택 시 카페만, 농장·주차장 제외 |
| 혼합 기록-맛집 | 치킨이 맛있었다는 기록 | 음식점 추천, 메뉴 판매 검증 없는 단정 금지 |
| 자연 계정 | 산·공원 기록 다수 | `nature`에서 관련 장소 지속 추천 |
| 혼합 지역 | 광주·대구 기록 혼합 | 지정한 지역으로만 검증된 장소 추천 |
| 무관한 후보 | 넓은 주차장, 조용한 농장 | 선택 분야 불일치로 제외 |
| 적합 후보 0·1·2·3+ | 단계별 mock | 각각 0·1·2·최대3 반환 |
| LLM 빈 배열 | 적합 장소는 존재 | 안전한 근거 기반 fallback |
| 후보 소진 | 같은 카테고리에서 refresh 반복 | 중복 최소화, 소진 후 최초 풀 복귀 |
| 빠른 분야 변경 | `cafe`→`bar` | 늦게 도착한 cafe 응답이 bar 화면을 덮지 않음 |

**측정 지표(목표치 확정 전)**: 분야 정확도(category adherence), 출처로 확인된 개인화 이유 비율(evidence support), 사용자가 직접 평가한 상위 3곳 관련성, 0곳 반환 비율, 응답 시간 중앙값/P95, 요청당 호출량·비용. 기존 두 계정은 필수 회귀셋이며, 가능한 한 기록 조합을 늘린다.

## 12. 작업 보호 조건 및 전달 방식

- 현 브랜치 `feature/fullstack-ujin`의 **모든 미커밋 변경사항 보존**.
